## Context

Task 03 turns the reviewed logical model into PostgreSQL tables that every later task builds on: import (08/09),
Database Explorer generic edits (11–13), Prospection/Home aggregates (14/16), audit/provenance (05/19) and, later,
agents sharing the same database. Several choices are cross-cutting and must be made once: identifier type,
timestamps, how fixed value sets are stored, constraint naming, deletion behaviour, normalization/uniqueness, and
which invariants the database itself guarantees. The repository is public and the data is personal: the schema must
not make later compliance work (opposition, erasure, audit) impossible.

## Decision

### Identifiers — UUID everywhere

Every table has a `uuid` primary key. The ORM generates **UUIDv7** (`uuid.uuid7()`, time-ordered: good B-tree
locality, creation-ordered ids); the column also has `DEFAULT gen_random_uuid()` so raw SQL inserts (Database
Explorer, scripts) work. UUIDs can be generated by any writer (future IProspect/IContact agents, imports, other
services) without a shared sequence, don't leak row counts in URLs, and let records be referenced across systems
before they are inserted. The join table `company_activity_categories` uses its composite key.

### Timestamps

`timestamptz` only. `created_at`/`updated_at` default to `now()` (transaction time). `updated_at` is maintained by a
`BEFORE UPDATE` trigger `set_updated_at` on every table that has the column (ORM `server_onupdate=FetchedValue()`),
so ORM, Core and raw-SQL writes all bump it. Append-only tables (`audit_log`, `contact_tracking_status_history`) and
write-once `import_row_metadata` have no `updated_at`. `audit_log.occurred_at` and `status_history.changed_at` use
`clock_timestamp()` so several entries written in one transaction stay ordered.

### Fixed technical value sets — `varchar(32)` + CHECK, never native enums

Business taxonomies (roles, commercial segments, activity categories, referents) are **tables**. Fixed technical
sets (`activity_status`, `contactability_status`, `verification_status`, `origin_type`, phone `type`, contact
tracking `status`, `source_type`, import `status`, `actor_type`, `civility`) are Python `StrEnum`s stored as
`varchar(32)` with a CHECK constraint `ck_<table>_<column>` (SQLAlchemy `Enum(native_enum=False,
create_constraint=True)`). Adding/removing a value is a one-line `DROP/ADD CONSTRAINT` migration inside a
transaction, with no `ALTER TYPE` restrictions and no type objects to manage. Migrations spell the value lists as
literals (they never import application code); a test compares every CHECK list with its Python enum because
Alembic autogenerate does not compare CHECK constraints.

### Constraint naming

`Base.metadata` carries a naming convention (`pk_<table>`, `fk_<table>_<column>_<referred table>`,
`uq_<table>_<columns>`, `ck_<table>_<name>`, `ix_<column label>`). Expression/partial/multi-column indexes are named
explicitly (`uq_…` when unique, `ix_…` otherwise). Names longer than PostgreSQL's 63 characters are shortened by hand
(two FKs) rather than left to hash truncation. Migrations use `op.f()` with the full names, so every constraint can
be referenced deterministically later.

### Deletion rules

| Relationship | ON DELETE | Why |
|---|---|---|
| taxonomy / referent ← companies, prospects, company categories, contact tracking | RESTRICT | Stable IDs; in-use values are deactivated (`active = false`), never deleted |
| company ← prospects | RESTRICT | A company never silently takes people with it |
| company ← establishments, category links | CASCADE | Pure company composition, no personal data |
| prospect ← emails, phones, contact_tracking (← history), prospect_sources, import_row_metadata | CASCADE | Parts of the person's record: erasing a person must erase their personal data in one statement; the audit log (no FK) keeps the trace |
| import batch ← prospect_sources | RESTRICT | A batch cited as provenance cannot disappear |
| import batch ← import_row_metadata | CASCADE | Row metadata has no meaning without its batch |
| company ← import_row_metadata | SET NULL | Keep the import-row trace if a company is removed |
| audit_log | no FKs | Entries must outlive the rows they describe |

A **do-not-contact prospect cannot be deleted** (trigger): deleting it would erase the opposition and a later
re-import would recreate the person as contactable. The explicit path is clear-then-delete, both audited. Whether
opposition records must instead be kept as a minimal suppression entry is a retention decision still open
(`open-questions.md` #2). The ORM defines no reverse relationships from taxonomies/companies to referencing rows, so
it can never null or delete a RESTRICT-protected reference on the database's behalf.

### Normalization and uniqueness

- Stored values are normalized so uniqueness is exact: SIREN (`^[0-9]{9}$`), SIRET (`^[0-9]{14}$`), email address
  and company `email_domain` lowercase without spaces, phone numbers digits with optional leading `+`. Services and
  the import normalize before writing; the CHECKs reject anything that slipped through. With normalized storage, a
  plain btree index serves case-insensitive equality (no `lower()` index needed on `emails.address`).
- `siren`/`siret` are plain `UNIQUE` constraints: PostgreSQL treats NULLs as distinct, so many unknown values are
  allowed.
- Taxonomy `slug` is unique (lowercase, hyphenated, CHECKed) and is the stable machine key used by seeds; `label` is
  unique case-insensitively (`uq_<table>_lower_label` on `lower(label)`), inactive rows included, so a user reactivates
  instead of duplicating.
- Email addresses are unique **per prospect** (`uq_emails_prospect_id_address`) but not globally: the legacy workbook
  shares addresses between rows, and deciding whether they are the same person is an import/dedup concern (Task
  08/09), not a storage error. Same for phones.

### Invariants enforced by the database

Partial unique indexes: one primary email / phone per prospect (`WHERE is_primary`, with CHECK
`is_active OR NOT is_primary` so a primary is always active), one primary establishment per company. `UNIQUE
(prospect_id)` on `contact_tracking` (one current cycle in V1; multi-cycle would become a partial unique index on an
`is_current` flag). CHECKs: do-not-contact consistency (`do_not_contact` ⇔ `do_not_contact_at` set; contactable ⇒
date and reason empty), at least one non-blank name per prospect, non-blank labels, history rows record an actual
status change, import batch `committed` ⇔ `committed_at`.

Two plpgsql triggers carry rules the ORM alone could not guarantee against generic write paths:

- `prospects.guard_do_not_contact` — rejects any UPDATE that turns `do_not_contact` back into `contactable` unless the
  transaction-local setting `viper.allow_contactability_clear = 'on'` is set, and rejects DELETE of a
  `do_not_contact` prospect. Only `repositories.prospects.write_cleared_contactability`, called by
  `services.prospects.clear_do_not_contact` (mandatory reason), sets the flag and switches it off right after its
  flush. Imports, contact-tracking updates and Database Explorer edits therefore cannot reactivate a blocked prospect
  even by mistake. This is a guard against accidents, not a security boundary: the application role owns the tables.
- `audit_log.append_only` / `no_truncate` — reject UPDATE, DELETE and TRUNCATE on `audit_log`.

Errors raised by these triggers use SQLSTATE `23001 restrict_violation`, so they surface as `IntegrityError` like
any other constraint violation.

### Actor snapshot

`app/core/actor.py` defines `ActorType` (`human | import | system | agent`) and the `ActorContext` dataclass
(`type`, `display`, optional opaque `id`); Task 04 builds it from the authenticated session. Every mutation service
takes it as its second argument. Tables that record who acted store a snapshot — `actor_type`, `actor_id`
(`varchar(128)`, opaque: a VIPER user UUID today, any future identity provider subject or agent id tomorrow),
`actor_display` — rather than a FK, because actors of different kinds have no common table and labels must not change
retroactively.

### Migrations and seeds

Migrations are hand-written and reviewed against `alembic revision --autogenerate`; tests check the ORM/migration
diff, CHECK names, enum values, the `updated_at` trigger on every timestamped table, and that every FK is the
leading column of a non-partial index. Seed data (suggested roles, segments, activity categories) is **not** a
migration: `python -m app.seed` inserts missing suggestions with `ON CONFLICT DO NOTHING` and never touches existing
rows, so it is idempotent and respects renames/deactivations.

## Consequences

- The database rejects most data-integrity mistakes regardless of the write path, which matters because Task 12
  adds generic grid writes and Task 09 bulk imports. Violations arrive as `IntegrityError` with a deterministic
  constraint name that services can translate into French UI messages.
- Services must normalize inputs (lowercase emails/domains, strip phone formatting, digits-only SIREN/SIRET) before
  writing; the import must map garbage to diagnostics or `legacy_metadata`, never force it into typed columns.
- New tables with `updated_at` must add the trigger in their migration (a test fails otherwise); new enum values
  need a migration replacing the CHECK (a test fails otherwise).
- A prospect flagged do-not-contact cannot be erased without first clearing the flag through the audited operation;
  the retention/erasure policy must be decided before production use (open question #2).
- `audit_log` is immutable from the application. A future retention/anonymization policy will need an explicit,
  reviewed migration or maintenance role to purge or redact entries — which is the intended friction.
- Substring search (`ILIKE '%x%'`) is not indexed yet; Task 17 decides on `pg_trgm` (the extension is available in the
  `postgres:16-alpine` image).

## Alternatives considered

- **Bigint identity keys** — smaller and naturally ordered, but need a central sequence for any writer and expose
  counts; UUIDv7 gives ordering without those drawbacks.
- **Native PostgreSQL enums** — typed at the database level, but `ALTER TYPE … ADD VALUE` has transaction
  restrictions, values cannot be removed or renamed without recreating the type, and the SQL console/explorer gains
  nothing over a CHECKed text column.
- **Lookup tables for technical enums** — maximal flexibility, but the sets are code-level semantics (status logic in
  counters, the contactability guard), not user data; a table would invite editing values the code depends on.
- **ORM-only `updated_at` (`onupdate=func.now()`)** — misses raw SQL and some bulk paths; the trigger is one function.
- **Service-only do-not-contact guard** — enough for code that goes through `ProspectService`, but generic explorer
  writes and future agents writing to a shared database would bypass it silently.
- **`citext` for emails/labels** — adds an extension and hides normalization; explicit lowercase storage plus
  `lower(label)` indexes keep behaviour visible in plain SQL.
- **Global unique email address** — would make legacy duplicates impossible to import and turn a dedup decision into
  a hard error.
